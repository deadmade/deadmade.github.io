## Things the drawing shows that are false or misleading

1. **The order of validation and review.** Both SVGs show Jedi, then mypy, then a return over LSP to review, then accept. That reads as "the developer reviews types mypy has already validated". This is only true for the lightbulb code action (`code_action_helper.py:131`). The main review surface, inlay hints, shows types mypy has not checked (`server.py:222-233`; `inlay_hint_helper.py:165-170` hardcodes `is_valid=True`). On Alt+Enter, mypy runs after the accept, and a hinted annotation can be silently dropped.
2. **Accept as a purely local step.** The drawing shows accept turning directly into "type annotations" inside VS Code, with one LSP round trip in total. In the code, accept starts a second LSP request. The server re-infers, writes the annotation with libcst, validates it with mypy and sends back a whole-file edit, which VS Code applies (`insertCommands.ts:44-79`, `server.py:298-355`).
3. **"Insert All" is not an accept.** For a whole file, the extension shows only a read-only diff preview and applies nothing (`insertCommands.ts:113-133`). If the drawing is read as covering bulk annotation, accept does not write the file in that path.

## Components or data paths the drawing leaves out

1. **libcst insertion engine** (`code/lsp/src/fangtype/insertion/`): the server, not VS Code, rewrites the source and returns it as a WorkspaceEdit.
2. **The project's own inference passes and the mypy worker process**: call-flow, contract and override propagation and type recovery around Jedi (`inference/`). mypy runs in a separate long-lived subprocess the server spawns (`validation/mypy_runner.py`).
3. **mypy diagnostics and annotation removal**: mypy also reports ordinary errors to the editor on open and save (`server.py:157-161,261-286`), and the tool can remove annotations (`server.py:435-504`). Neither appears in the drawing.

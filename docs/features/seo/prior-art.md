## Comparable implementations

1. **jekyll-seo-tag**, GitHub Pages' SEO plugin ([template.html](https://raw.githubusercontent.com/jekyll/jekyll-seo-tag/master/lib/template.html)). One `<script type="application/ld+json">` block plus `og:*` and `twitter:*` tags; `og:image:width/height/alt` when the image has them; `og:type` article or website by `date_published`; `google-site-verification` and `msvalidate.01` from `webmaster_verifications` config. Decision that matters: image width, height and alt are first-class fields, and verification tags come from config.
2. **PaperMod** ([schema_json.html](https://raw.githubusercontent.com/adityatelange/hugo-PaperMod/master/layouts/_partials/templates/schema_json.html)). The home page gets `Organization` by default, or `Person` via `schema.publisherType` (name, url, description, sameAs); regular pages get two separate `ld+json` blocks, `BreadcrumbList` and `BlogPosting`. `sameAs` comes from `params.schema.sameAs`, else from the social icons.
3. **Blowfish** ([schema.html](https://raw.githubusercontent.com/nunocoracao/blowfish/main/layouts/partials/schema.html)). The home page gets `WebSite` with a `Person` publisher; other pages get `Article` with an author `Person` (with `sameAs`) and `dateModified` from `.Lastmod`. The `WebSite` node sits on the home page only, matching Google's site-name rule.
4. **Hugo embedded templates** ([Embedded templates](https://gohugo.io/templates/embedded/), source [opengraph.html](https://raw.githubusercontent.com/gohugoio/hugo/master/tpl/tplimpl/embedded/templates/_partials/opengraph.html)). `opengraph.html` emits url, site_name, title, description, locale, type and up to 6 `og:image`, with no width, height or alt; `og:type` is "`article` for pages and `website` for list and home pages"; `article:published_time` only with a `.PublishDate`, `article:modified_time` from `.Lastmod`. `twitter_cards.html` uses `summary_large_image` when an image exists. `schema.html` emits microdata `meta` elements in `<head>` (name, description, dates, wordCount, image, keywords).

## Official docs: constraints that shape the design

- **Site names** ([Google](https://developers.google.com/search/docs/appearance/site-names)): `WebSite` structured data on the home page is "most important"; `og:site_name`, `<title>` and headings are also read. JSON-LD, RDFa and microdata are accepted (the microdata example is a `<div itemscope>` of `<link itemprop="url">` and `<meta itemprop="name">` in the body). Domain- and subdomain-level sites are supported. `alternateName` is strongly considered as a fallback; the lowercase domain is the last resort. Keep the site-name properties in one node and avoid an additional `WebSite` block "if you can help it". Not supported by the Rich Results Test; use a schema testing tool (for example the Schema Markup Validator) or URL Inspection.
- **ProfilePage** ([Google](https://developers.google.com/search/docs/appearance/structured-data/profile-page)): requires `mainEntity` (a Person or an Organization) and its `name` (or `alternateName`); recommends `dateModified`, `alternateName`, `image`, `sameAs`. "The primary focus of the page must be a single person or organization that is affiliated with the overall website." Valid: "An 'About Me' page on a blog site"; invalid: a store's home page. The feature's stated purpose is creators in online communities (Discussions and Forums).
- **General guidelines** ([Google](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)): JSON-LD recommended, microdata and RDFa supported; don't mark up content that is not visible to readers; the markup must be a true representation of the page.
- **Favicon** ([Google](https://developers.google.com/search/docs/appearance/favicon-in-search)): `<link rel="icon">` in the home page's head; square, at least 8×8, "we recommend using a favicon that's larger than 48x48px"; formats BMP, GIF, ICO, PNG, JPEG, PPM and TIFF (no SVG or WebP); stable URL, crawlable by Googlebot-Image; not guaranteed.
- **Sitemap lastmod** ([Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)): `priority` and `changefreq` are ignored; `lastmod` is used only if consistently and verifiably accurate; a copyright-date change is not significant.
- **Hugo sitemap** ([sitemap](https://gohugo.io/templates/sitemap/), [embedded source](https://raw.githubusercontent.com/gohugoio/hugo/master/tpl/tplimpl/embedded/templates/sitemap.xml)): `<lastmod>` is written only when `.Lastmod` is non-zero. [`enableGitInfo`](https://gohugo.io/methods/page/gitinfo/) makes Lastmod the author date of the file's last commit; in a shallow clone it "may be inaccurate"; GitHub Pages needs `fetch-depth: 0`. [`[frontmatter]`](https://gohugo.io/configuration/front-matter/) default `lastmod` order: `:git`, `lastmod`, `modified`, `date`, `publishdate`, …
- **Open Graph** ([ogp.me](https://ogp.me/)): required `og:title`, `og:type`, `og:image`, `og:url`; "If the page specifies an og:image it should specify og:image:alt".
- **Verification** ([Search Console](https://support.google.com/webmasters/answer/9008080), [Bing](https://www.bing.com/webmasters/help/add-and-verify-site-12184f8b)): Google offers an HTML file, a meta tag, Analytics, Tag Manager, hosting platforms and DNS; DNS "is the only way to verify a Domain property" and needs control of the domain. Bing offers import from Search Console, an XML file, a meta tag, CNAME and DNS auto verification. [IndexNow](https://www.indexnow.org/documentation) needs a key text file within the host (the root recommended).
- **Custom domain** ([GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site)): with an Actions workflow no `CNAME` file is used; apex and `www` redirect automatically; verify the domain and avoid wildcard DNS records (takeover risk).
- **AI crawlers**: [OpenAI](https://developers.openai.com/api/docs/bots): OAI-SearchBot (search) and GPTBot (training) are set independently; ChatGPT-User is user-initiated and robots.txt "may not apply". [Anthropic](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler): ClaudeBot (training), Claude-SearchBot, Claude-User. [Perplexity](https://docs.perplexity.ai/docs/resources/perplexity-crawlers.md): PerplexityBot (search, not training), Perplexity-User "generally ignores robots.txt". [Google](https://developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers): Google-Extended is a robots.txt control token and does not affect Search.
- **Google and AI** ([AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide), [AI features](https://developers.google.com/search/docs/appearance/ai-features)): "You don't need to create new machine readable files, AI text files, markup, or Markdown"; Google Search ignores llms.txt; no special schema.org data is needed. The two pages differ on eligibility: "no additional technical requirements" versus "a site must be included in Search generative AI features in Search Console".

## Approaches

**A. Meta tags only (as now).** Hugo's `opengraph.html` and `twitter_cards.html`, no structured data. Good at: no markup to keep in step, no `<script` (it writes only `<meta>`). Costs: no `WebSite` node, so the site name rests on weaker signals [source: site names]; no image size or alt [source: opengraph.html, ogp.me].

**B. JSON-LD** (jekyll-seo-tag: one block; Blowfish; PaperMod: two blocks on regular pages). The home page gets `WebSite` and a `Person` (or a publisher), built from config. Good at: Google's recommended format [source: sd-policies]. Costs: a `<script type="application/ld+json">`, so `check-site.py` must allow that one type [inferred; not executable JavaScript, which no fetched page states].

**C. Microdata** (Google's site-name and ProfilePage examples). `itemscope` and `itemprop` attributes, or a standalone `<div itemscope>` of `<meta>` and `<link>` elements as in Google's example. Good at: officially supported for site names and ProfilePage, no script [source]. Costs in this codebase [inferred, from the code]: `check-site.py` collects every `<link>` and fails one that leaves the site, so a `<link itemprop="sameAs" href="https://github.com/…">` needs a change there too; properties on visible elements must sit inside the `itemscope` element in the page tree.

**D. Hugo `schema.html` (head microdata).** Describes a generic page (name, dates, wordCount), not `WebSite` or `Person`, so it does not set the site name [inferred from its field list].

## Pitfalls seen in sources

- Regular pages from Hugo's template are typed `article`; `Lastmod` is zero without Git info or front-matter dates [sources: opengraph.html, sitemap.xml, `[frontmatter]`].
- A shallow clone can give every page the newest repository commit as its date [Hugo GitInfo page]; this repo's CI uses `fetch-depth: 0`.
- Google asks for one `WebSite` node and no additional `WebSite` block where avoidable [site names].
- Marking up content that is not visible is against the quality guidelines [sd-policies].
- Blog claim (not official): LinkedIn reads only Open Graph and standard meta tags, uses 1200×627, and caches about 7 days; the Post Inspector refreshes it ([previewog.com](https://previewog.com/linkedin-meta-tags/), blog).
